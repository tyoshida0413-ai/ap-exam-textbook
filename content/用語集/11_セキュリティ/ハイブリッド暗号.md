# ハイブリッド暗号

> 本文を[[共通鍵暗号方式]]で暗号化し、その共通鍵を[[公開鍵暗号方式]]で相手に送る方式。速度と鍵配送の両方を解決する。

## 日常のたとえ

**「いいとこ取り」の宅配便**です。

共通鍵暗号は「速いが、鍵をどう相手に安全に渡すか」が問題でした。
公開鍵暗号は「鍵を安全に渡せるが、荷物（本文）を運ぶには遅すぎる」という問題がありました。

そこで、**軽い鍵だけ安全な特別便（公開鍵暗号）で送り、重い荷物（本文）は普通の速い便（共通鍵暗号）で送る**、
というのがハイブリッド暗号です。

## なぜそうなるのか

```
(1) 公開鍵暗号（遅いが安全に渡せる）を使って、「共通鍵」だけを相手に渡す
(2) 渡し終わったら、あとは共通鍵暗号（速い）で本文をやりとりする
```

**渡すのは小さな鍵1個だけなので、遅くても問題ありません。**
本文は大量なので、速い方式で処理します。**互いの欠点が消えます。**

これは理論上の組み合わせではなく、あなたがWebサイトを見るとき（https://）に
実際に[[SSL/TLS]]の中で毎回起きている処理です。

```
(1) サーバがディジタル証明書を提示
(2) クライアントがCAの署名を検証して真正性を確認
(3) 鍵交換により、その通信限りの「共通鍵（セッション鍵）」を安全に共有
(4) 以降は共通鍵暗号で高速に本文をやりとり
```

## 混同しやすい語

| 語 | 決定的な違い |
|---|---|
| [[共通鍵暗号方式]] | ハイブリッド暗号は共通鍵暗号「だけ」ではない。**鍵の受け渡し部分だけ**公開鍵暗号を使う |
| [[公開鍵暗号方式]] | 本文の暗号化に公開鍵暗号を使うわけではない。**遅いので鍵の受け渡しだけ**に使う |

## 試験での問われ方

- 「共通鍵暗号方式と公開鍵暗号方式を併用する理由を述べよ」（記述式の典型）
  → **共通鍵暗号は高速だが鍵配送に問題があり、公開鍵暗号は鍵配送に強いが低速であるため、
  鍵の配送に公開鍵暗号、本文の暗号化に共通鍵暗号を使い両者の欠点を補い合う**
- SSL/TLSの仕組みを問う設問の中で、この構造の理解が前提になる
