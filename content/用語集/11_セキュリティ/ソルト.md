# ソルト

> パスワードをハッシュ化する前に混ぜる、**利用者ごとに異なるランダムな文字列**。
> 同じパスワードでも保存される値が全員バラバラになり、[[レインボー攻撃]]を無効化する。

## 日常のたとえ

**同じ料理でも、人ごとに違う隠し味を入れておく**ようなものです。

「カレー」という同じ料理でも、Aさんの分にはコーヒーを、Bさんの分にはチョコレートを
ひと匙ずつ入れておけば、**出来上がった味は全員違うもの**になります。

すると、「カレーの味の見本帳」を持っている人がいても、
**どれとも一致しないので照合できません**。これがソルトの効果です。

## なぜそうなるのか

### まず前提：パスワードはそのまま保存しない

まともなシステムは、パスワードを平文では保存せず、[[ハッシュ関数]]という
**元に戻せない変換**をかけて保存します。
そうすればデータベースが盗まれても、そこにあるのは意味不明な文字列だけ ── のはずでした。

### ところが攻撃者は「対応表」を作った

```
password  →  5f4dcc3b5aa765d61d8327deb882cf99
123456    →  e10adc3949ba59abbe56e057f20f883e
qwerty    →  d8578edf8458ce06fbc5bb76a58c5ca4
```

よく使われるパスワードを片っ端から変換して**表にしておけば、引くだけで元が分かります**。
これが[[レインボー攻撃]]です。ハッシュ化しただけでは防げません。

### そこでソルトを混ぜる

```
Aさん： password + "x7fk2q"  → 変換 → 全然違う値
Bさん： password + "m9r3zt"  → 変換 → また全然違う値
```

**同じ "password" なのに、保存される値が全員バラバラ**になります。
攻撃者が事前に用意した対応表は、**まったく役に立たなくなります**。

### ソルトは秘密にしなくてよい

ソルトは通常、ハッシュ値と一緒に保存されます（照合時に必要なため）。
**秘密にできなくても効果は失われません。**
目的は「隠すこと」ではなく、**事前計算した表を使えなくすること**だからです。

ただしソルトだけでは、1人分を狙った総当たりは防げません。
そのため[[ストレッチング]]（変換を数千〜数万回繰り返す）と**セットで使います**。

## 混同しやすい語

| 語 | 決定的な違い |
|---|---|
| [[ストレッチング]] | **時間を稼ぐ**対策（繰り返して1回の計算を重くする）。ソルトは**表を無効化する**対策。目的が別 |
| 暗号化 | ソルトはハッシュの**前処理**。暗号化のように元へ戻すことは想定していない |

## 試験での問われ方

- 「ソルトを用いる目的はどれか」
  → **同一のパスワードでも異なるハッシュ値とし、レインボー攻撃を困難にする**
- ひっかけ：「ハッシュ値から元のパスワードを復元可能にする」＝誤り（ハッシュは戻せない）
- ストレッチングとセットで、**どちらが何を防ぐか**を入れ替えて問われる
