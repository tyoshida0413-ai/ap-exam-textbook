# RFC

> **変更要求**。[[変更管理]] において、何を、なぜ、いつ変えたいかを示す**正式な申請**。変更のプロセスはこのRFCの起票から始まる。

## なぜそうなるのか

思いつきで変更を実施させないために、変更管理では最初に**書面での申請**を求めます。
これがRFCです。RFCには「何を変えるのか」「なぜ変える必要があるのか」「いつ実施したいか」
「失敗した場合の切戻し手順（[[切戻し計画]]）」などを記載します。

RFCに記載すべき代表的な項目は次のとおりです。

| 項目 | 内容 |
|---|---|
| 変更の内容 | 何を、どのシステム・サービスに対して変更するか |
| 変更の理由 | なぜ必要か（不具合の修正、機能追加、法令対応など） |
| 影響範囲 | どのサービス・利用者に影響するか（[[CMDB]] で確認） |
| 実施予定日時 | いつ実施したいか |
| 切戻し計画 | 失敗した場合にどう戻すか |
| 申請者・承認者 | 誰が申請し、誰が承認するか |

RFCが起票されると、[[構成管理|CMDB]] を使った影響評価を経て、
[[CAB]]（変更諮問委員会）による審議・承認へと進みます。
**RFCが無ければ、そもそも変更管理のプロセスが始まりません。**
口頭での依頼や、担当者個人の判断による変更実施を許してしまうと、
**「誰が、いつ、何のために変更したか」の記録が残らず**、
後で障害が起きたときの原因調査（[[問題管理]]）も困難になります。

RFCの記録は、変更が実施された後も**過去の変更履歴**として蓄積されていきます。
新しいインシデントが発生したときに「直近でこのサーバに関わる変更はあったか」を
RFCの履歴から調べることで、**原因の絞り込みが格段に速くなる**という副次的な効果もあります。

## 混同しやすい語

| 語 | 決定的な違い |
|---|---|
| [[CAB]] | あちらは**RFCを審議して承認する会議体**／こちらは**審議の対象となる申請書そのもの** |

## 試験での問われ方

- 「RFCの説明として適切なものはどれか」
  → **変更を求める正式な申請であり、変更管理プロセスの起点となる**
