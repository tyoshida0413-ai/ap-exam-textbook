# RTO

> Recovery **Time** Objective ＝ **目標復旧時間**。障害発生から**どれだけの時間内に復旧させるか**の目標値。[[RPO]] が「どの時点まで」を決めるのに対し、こちらは「**いつまでに**」を決める。

## 日常のたとえ

停電したとき、「懐中電灯なら数秒で使える」「非常用電源なら数分で復旧する」「電力会社の復旧を待てば数時間」──
どこまで許容できるかで、備えるべき手段が変わります。
「4時間以内に電気を戻したい」という目標が決まって初めて、必要な設備が決まります。

## なぜそうなるのか

[[サービス継続管理]] では、復旧の目標を2つの向きから決めます。

```
前回バックアップ         障害発生           復旧完了
     │                     │                   │
     ├──────────────────→│←─────────────────→│
     │   ← RPO の範囲 →    │    ← RTO の範囲 →   │
     │  （失ってよいデータ）│  （止まってよい時間）│
```

- **RTOは障害発生よりも「未来」を向いている** ── いつまでに戻すか
- **[[RPO]] は障害発生よりも「過去」を向いている** ── どこまで巻き戻るか

RTOを短くするほど、常時稼働する予備設備（[[バックアップサイト]] のホットサイトなど）が必要になり、
**設備の費用が上がります**。逆にRTOが長くてよいなら、コールドサイトのような安価な備えで足ります。

RTOと[[RPO]]は独立して決まる点も重要です。
「4時間で復旧するが1日ぶんのデータは失われる」設計も、
「データは1件も失わないが復旧に3日かかる」設計も、どちらもありえます。

## 混同しやすい語

| 語 | 決定的な違い |
|---|---|
| [[RPO]] | あちらは **Point＝時点**（どこまでデータを戻すか）／こちらは **Time＝時間の長さ**（何時間で戻すか）。**最頻出のひっかけ** |
| [[RLO]] | あちらは **Level＝水準**（100%か縮退か）／こちらは**時間の長さ** |
| [[バックアップサイト]] | あちらは**RTOを達成するための手段**（設備）／こちらは**達成すべき目標値** |

## 試験での問われ方

- 「RTOの説明として適切なものはどれか」→ **障害発生から復旧までに許容される時間の目標値**
- **最頻出のひっかけ**：RTOとRPOの説明の入れ替え。**Time＝時間、Point＝時点**と押さえる
- **科目B（記述式）**：「RTOとRPOの違いを述べよ」
  → **RTOは何時間以内に復旧するかの目標、RPOはどの時点のデータまで復旧するかの目標**
