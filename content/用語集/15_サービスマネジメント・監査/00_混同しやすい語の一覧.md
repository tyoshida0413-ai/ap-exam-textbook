# サービスマネジメント・監査 混同しやすい語の一覧

> **2つの使い方がある**
> (1) **学習用**：試験で狙われるのは「似た語の取り違え」。ここだけ潰せば失点が大きく減る
> (2) **作業用**：用語集を書くときの設計図（→ 3章の難語リストが執筆の優先順位になる）

> **この分野の大原則**
> この分野の語は、**ほとんどが「今を戻す」か「二度と起こさない」かのどちらか**です。
> インシデント管理⇔問題管理、修正⇔是正処置、可用性管理⇔継続管理、ワークアラウンド⇔恒久対策。
> **同じ構造が名前を変えて何度も出てきます。**
>
> そして**この分野は計算も作図もほとんどありません**。
> 代わりに、**「似た言葉を入れ替えて誤答させる」のが出題の中心です。**
> だから、**対比で覚えていない語は本番でほぼ確実に落とします**。
> 逆に言えば、**下の1章の表を説明できるようになるだけで、得点が安定します**。

## 1. 最重要の混同ペア（ここを間違えると失点が大きい）

| 対比 | 決定的な違い | ひっかけの出方 |
|---|---|---|
| [[インシデント管理]] ↔ [[問題管理]] | **早く戻す**（原因は追わない）／**根本原因を除去して再発を防ぐ** | 目的の説明を入れ替える。**この分野で最頻出** |
| [[ワークアラウンド]] ↔ 恒久対策 | **原因を残したまま業務を戻す**／原因そのものを除去する | 「再起動で復旧した」を問題解決と扱わせる |
| [[変更管理]] ↔ [[リリース及び展開管理]] | **やってよいかを決める**（意思決定）／**実際に届ける**（実行） | 役割を入れ替える |
| [[構成管理]] ↔ [[資産管理]] | **要素どうしの関係**を把握する（影響範囲）／**持ち物としての価値**を管理する（財務） | 取得価額・減価償却を構成管理の目的にする |
| [[可用性管理]] ↔ [[サービス継続管理]] | **日常の障害**に備えて止まらなくする／**災害級の事象**を前提に早く再開する | 冗長化と代替サイトを入れ替える |
| [[RTO]] ↔ [[RPO]] | **何時間で戻すか**（時間の長さ）／**どの時点のデータまで戻すか**（データの鮮度） | 説明の入れ替え。**Time＝時間、Point＝時点** |
| [[SLA]] ↔ [[OLA]] ↔ [[UC]] | **顧客と**／**社内部門どうしで**／**外部の供給者と** | 顧客への約束を支える側の契約が抜けている事例を出す |
| [[サービスカタログ]] ↔ [[サービスポートフォリオ]] | **提供中だけ**（顧客が見る）／**計画中・提供中・廃止済みの全部**（社内用） | 包含関係を逆にする |
| [[ITIL]] ↔ [[JIS Q 20000]] | **ベストプラクティス集**（認証されない）／**規格**（組織が認証を取得できる） | 「ITIL認証を取得した企業」＝誤り |
| [[事業関係管理]] ↔ [[サービスレベル管理]] | **顧客の事業そのもの**を見る（御用聞き）／**合意した数値**を見る（通信簿） | 顧客満足度とSLA達成率を入れ替える |
| [[容量・能力管理]] ↔ [[需要管理]] | **どれだけ応えられるか**（出口）／**どれだけ求められるか**（入口） | どちらが予測でどちらが確保か |
| インシデント ↔ [[サービス要求管理\|サービス要求]] | **計画外の中断・品質低下**／**あらかじめ想定された定型の依頼** | パスワード再発行をインシデントとして数えさせる |
| [[不適合及び是正処置\|修正]] ↔ [[不適合及び是正処置\|是正処置]] ↔ [[予防処置]] | **不適合そのものを直す**／**原因を除去して再発を防ぐ**／**まだ起きていない原因を除去する** | 修正を是正処置と呼ばせる |
| [[内部監査]] ↔ [[マネジメントレビュー]] | **監査員**が実施状況を見る／**経営層**がSMS全体の妥当性を見直す | 実施主体を入れ替える |
| [[IT全般統制]] ↔ [[IT業務処理統制]] | **IT環境そのもの**を守る（前提）／**1件ごとの処理**の正確性を守る | 入力チェックを全般統制にする。**監査で最頻出** |
| [[保証型監査]] ↔ [[助言型監査]] | **適切であると表明する**／**改善の提言を行う** | 監査人が改善を実施する選択肢を混ぜる |
| [[システム監査基準]] ↔ [[システム管理基準]] | **監査人**の行為規範／**被監査側**のあるべき姿（＝判断尺度） | 誰のための基準かを入れ替える |
| [[監査調書]] ↔ [[監査報告書]] | **監査の実施記録**（内部・機密）／**結論と指摘**（依頼者へ提出） | 提出先と内容を入れ替える |
| [[テストデータ法]] ↔ [[並行シミュレーション法]] ↔ [[ITF法]] | **監査人のデータ**を本番処理へ／**本番データ**を監査人の処理へ／**本番処理の中に監査用の対象**を混ぜる | 3つを入れ替える |
| [[CSA]] ↔ [[内部監査]] | **当事者による自己評価**（独立性なし）／**独立した立場**での評価 | 「CSAは内部監査を代替する」＝誤り |
| [[UPS]] ↔ [[自家発電装置]] | **数分〜数十分をつなぐ**（安全に止めるため）／**長時間の停電に備える** | UPSの目的を「業務の継続」にする |
| [[予防保全]] ↔ 事後保全 | **壊れる前に**交換する／**壊れてから**直す | 「すべて予防保全にすべき」＝誤り（費用対効果） |

## 2. セットで理解すべき語のかたまり

### (A) サービスの一生は5段階で回る

[[サービスライフサイクル]]：戦略 → 設計 → 移行 → 運用 → [[継続的改善]] → 戦略へ戻る
[[サービスマネジメントシステム|SMS]] はこれをPDCAとして仕組み化したもの

> **SMSの「システム」はコンピュータではありません。**
> **方針・目標・プロセス・記録の集まり**、つまり**組織の仕組み**を指します。ここが定番のひっかけです。

### (B) 顧客への約束は、内と外の約束に支えられている

[[SLA]]（顧客と） ← [[OLA]]（社内部門どうし） ＋ [[UC]]（外部の供給者と）

> **試験の型**：顧客とのSLAは「4時間以内に復旧」なのに、
> 保守を委託している業者との契約（UC）が「翌営業日対応」になっている。
> **SLAを結ぶ前に、それを支えるOLAとUCを固める**のが正解です。

### (C) 止まったときの動きは「戻す → 掘る」の2段構え

インシデント発生 → [[インシデント管理]]（[[ワークアラウンド]]で業務を戻す）
→ [[問題管理]]（根本原因を掘る）→ [[既知の誤り]]（原因は判明・恒久対策はこれから）→ 恒久対策

> **順番を逆にしない。** 原因究明を先にすると、その間ずっと業務が止まります。
> 記述式で「まず何をすべきか」と問われたら、答えは**必ず「業務の復旧」です。**

### (D) 変えることのリスクは、承認と切戻しで管理する

[[RFC]]（変更要求）→ 影響評価（[[CMDB]] を見る）→ [[CAB]] が承認 →
[[リリース及び展開管理]] が実施 → レビュー

> **[[切戻し計画]] が無い変更は承認してはいけません。**
> 変更の失敗はゼロにできないので、**「戻せること」を承認の条件にする**のが変更管理の要点です。
> [[標準変更]] は、リスクが低く手順が確立しているため**あらかじめ包括承認**されているもの。

### (E) 「何があるか」を知らないと、変更もインシデントも扱えない

[[構成品目]]（CI）→ [[CMDB]] → [[構成管理]]

> **構成管理は [[変更管理]] と [[インシデント管理]] の土台**です。
> どのサーバがどのサービスに使われているかを知らなければ、
> **変更してよいかも、誰が困っているかも判断できません**。

### (F) 止まらない・戻せるは、指標で語る

[[可用性管理]]：MTBF ／ MTTR ／ 稼働率 ＝ MTBF ÷（MTBF ＋ MTTR）
[[サービス継続管理]]：[[BCP]] ／ [[BCM]] ／ [[RTO]] ／ [[RPO]] ／ [[RLO]] ／ [[バックアップサイト]]

> **稼働率を上げる方法は2つだけ**：**壊れにくくする**（MTBFを長く）か、**早く直す**（MTTRを短く）か。
> 試験で狙われるのは後者です。**予備機と手順書のほうが、安く効きます。**
>
> **バックアップサイトは温度が高いほどすぐ動けて、そして高い**（ホット → ウォーム → コールド）。

### (G) 運用は「決める人」と「やる人」が分かれている

[[運用オペレーション]]（日々の作業）／ システム運用管理（計画と基準）
[[サービスデスク]]（単一窓口）／ [[一次解決率]]（質を測る指標）
[[外形監視]] ／ [[バッチウィンドウ]] ／ [[チャットボット]]

> **サービスデスクの本質は「解決すること」ではなく「窓口を1つにすること」です。**
> 利用者に「これはネットワークの問題かアプリの問題か」を判断させないためにあります。

### (H) 評価と改善は、誰がやるかで名前が変わる

[[サービス報告]]（顧客へ）／ [[内部監査]]（監査員が）／ [[マネジメントレビュー]]（経営層が）
→ [[不適合及び是正処置]] ／ [[予防処置]] ／ [[継続的改善]]

### (I) 監査は「独立していること」がすべての前提

[[システム監査人]]（独立性）→ [[監査計画]] → [[予備調査]] → [[本調査]] →
[[監査証拠]] を [[監査調書]] に記録 → [[監査報告書]] → [[フォローアップ]]

> **監査人は助言はできても、改善を自ら実施してはいけません。**
> 実施すると、次の監査で**自分の仕事を監査する**ことになり、独立性が失われます。
> **改善の実施は被監査部門、実施状況の確認は監査人**、という分担を必ず押さえます。

### (J) 監査技法は「何を流すか」の2軸で整理する

| 技法 | 使うデータ | 使う処理 |
|---|---|---|
| [[テストデータ法]] | **監査人が作ったもの** | 本番の処理 |
| [[並行シミュレーション法]] | **本番のもの** | **監査人が作った処理**（結果を比較する） |
| [[ITF法]] | 本番のもの＋**監査用の擬似対象** | 本番の処理 |
| [[CAAT]] | 本番のもの（**全件**） | 監査用のツール |

### (K) 内部統制は「6つの要素」で組み立てる

[[内部統制の基本的要素]]：統制環境 ／ リスクの評価と対応 ／ 統制活動 ／
情報と伝達 ／ モニタリング ／ ITへの対応

[[統制環境]] が**土台**。**統制活動**の中心が [[職務分掌]]・[[相互牽制]]・[[職務のローテーション]]。
「ITへの対応」の中身が [[IT全般統制]] と [[IT業務処理統制]]。

> **内部統制は万能ではありません。**
> 判断の誤り／**複数人の共謀**／想定外の事象／**経営者による無効化**／費用と便益の均衡 ── の5つが限界です。
> 「内部統制を整備すれば不正は完全に防止できる」は**必ず誤り**。
>
> そして**職務分掌は共謀には無力**なので、[[職務のローテーション]]や強制休暇と組み合わせます。
