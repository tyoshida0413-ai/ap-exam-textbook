# インシデント管理

> サービスの計画外の中断や品質低下が起きたとき、**合意したサービスレベルへできるだけ早く回復させる**ための活動。**原因の究明は目的ではない**。

## 日常のたとえ

夜、部屋の照明が突然消えました。あなたは何をするでしょうか。

**「なぜ消えたのか」を調べ始める人はいません。**
まず懐中電灯をつけます。とりあえず生活できる状態に戻してから、明るくなってから原因を調べます。

インシデント管理は、この**懐中電灯をつけるほう**の活動です。
配線を調べて交換するのは [[問題管理]] の仕事で、**別の活動として分けられています**。

## なぜそうなるのか

分けている理由は単純で、**目的が違うと、正しい行動が変わってしまう**からです。

原因究明を優先すると、その間ずっと業務が止まります。
利用者にとって重要なのは「なぜ止まったか」ではなく「**いつ仕事に戻れるか**」です。
だから**インシデント管理は、原因が分からないまま解決してよい**という、
一見いい加減に見える割り切りを最初から持っています。

この「根本原因を除去しないまま業務を戻す手当て」を [[ワークアラウンド|ワークアラウンド（回避策）]] といいます。
再起動する、別のプリンタへ出力先を変える、代替の操作手順を案内する ── すべて正解です。

### インシデントの範囲

**「止まった」だけがインシデントではありません。**
**サービス品質の低下**も含みます。動いてはいるが極端に遅い、一部の機能だけ使えない ── これらもインシデントです。
定義を問う出題では、ここが狙われます。

### 対応の流れ

```
記録 → 分類 → 優先度付け → 調査・診断 → 解決・回復 → 終了
```

**記録は「必要と判断したものだけ」ではなく、受け付けたすべてを残します。**
記録の本当の価値は、後から**傾向を分析する**ことにあるからです（→ [[問題管理]]）。
担当者の判断で記録を省くと、この分析ができなくなります。

終了時には、**利用者に確認を取ってから閉じます**。
「直ったはず」で閉じると、同じ申告が繰り返されます。

## 混同しやすい語

| 語 | 決定的な違い |
|---|---|
| [[問題管理]] | あちらは**根本原因を除去して再発を防ぐ**（中長期）／こちらは**早く戻す**（今すぐ）。**この入れ替えが最頻出のひっかけ** |
| [[サービス要求管理]] | あちらは**計画内の定型の依頼**（パスワード再発行など）／こちらは**計画外の中断・品質低下** |
| [[変更管理]] | あちらは**これから変えることのリスク**を管理／こちらは**すでに起きた事象**への対応 |
| [[サービスデスク]] | あちらは**窓口という機能（組織）**／こちらは**プロセス（活動）**。サービスデスクはインシデント管理の入口を担う |

## 試験での問われ方

- 「インシデント管理の目的として適切なものはどれか」
  → **サービスをできるだけ迅速に復旧させ、事業への影響を最小限に抑える**
- **最頻出のひっかけ**：「インシデントの根本原因を特定し、再発を防止する」→ ✕。それは [[問題管理]]
- **優先度のひっかけ**：「受付順に対応する」「役職の高い人を優先する」→ ✕。
  優先度は [[インシデントの優先度|影響度と緊急度の組合せ]] で決める
- **科目B（記述式）の定番**：「インシデント発生時にまず何をすべきか」
  → **原因究明ではなく、暫定対応（ワークアラウンド）による業務の復旧**。
  この1点を書けるかどうかで大きく差が付きます
