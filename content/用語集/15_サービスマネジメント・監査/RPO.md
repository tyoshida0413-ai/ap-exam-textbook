# RPO

> Recovery **Point** Objective ＝ **目標復旧時点**。災害や障害からの復旧時に、**どの時点のデータまで戻すか**を定めた目標。言い換えれば「**最大でどれだけのデータを失ってよいか**」を決める指標。

## 日常のたとえ

レポートを書いているとき、あなたは何分おきに保存するでしょうか。

30分おきに保存する人は、パソコンが落ちたら**最大30分ぶんの作業が消える**ことを受け入れています。
自動保存を1分おきにすれば失うのは1分ぶんですが、**保存のたびに動作が重くなります**。

この「**失ってよい時間の長さ**」がRPOです。
ゼロにしたければ、書いた瞬間に別の場所へ書き写す仕組みが要り、そのぶん費用がかかります。

## なぜそうなるのか

[[サービス継続管理]] では、復旧の目標を**2つの向きから**決めます。

```
前回バックアップ         障害発生           復旧完了
     │                     │                   │
     ├──────────────────→│←─────────────────→│
     │   ← RPO の範囲 →    │    ← RTO の範囲 →   │
     │  （失ってよいデータ）│  （止まってよい時間）│
```

- **RPOは障害発生よりも「過去」を向いている** ── どこまで巻き戻るか
- **[[RTO]] は障害発生よりも「未来」を向いている** ── いつまでに戻すか

この2つは**独立して決まります**。
「4時間で復旧するが、1日ぶんのデータは失われる」という設計も、
「データは1件も失わないが、復旧には3日かかる」という設計も、どちらもありえます。

### RPOが決めるのは「バックアップの間隔」

| RPO | 意味 | 必要になる仕組み |
|---|---|---|
| **24時間** | 最大1日ぶんのデータは失ってよい | **1日1回のバックアップ**で足りる |
| **1時間** | 最大1時間ぶんまで | 1時間ごとの差分取得、ログの退避 |
| **0** | **1件も失えない** | **リアルタイムのデータ同期（ミラーリング）** |

**RPOを短くするほどバックアップの費用が上がり、[[RTO]] を短くするほど設備の費用が上がります。**
だから正しい問いは「どちらも最短にしよう」ではなく、
「**この業務は、どこまで失うと本当に困るのか**」です。

> **業務によって答えが変わります。**
> 銀行の勘定系は1件の取引も失えないのでRPOはほぼ0。
> 社内の勤怠システムなら「前日ぶんまで戻れば、あとは打ち直せる」ことが多く、RPOは24時間で足ります。
> **業務側と合意して決める**という点が、[[SLA]] と同じ発想です。

## 混同しやすい語

| 語 | 決定的な違い |
|---|---|
| [[RTO]] | あちらは **Time＝時間の長さ**（何時間で戻すか）／こちらは **Point＝時点**（どこまで戻すか）。**説明の入れ替えが最頻出** |
| [[RLO]] | あちらは **Level＝水準**（100%か、縮退した50%か）／こちらはデータの鮮度 |
| [[フルバックアップ]] | あちらは**取得方式**／こちらは**目標値**。RPOを決めると、必要な取得方式と間隔が決まる |
| MTTR | あちらは**平均修復時間**（実績の平均値）／こちらは**目標値**。似ているのはRTOのほうで、RPOとは別物 |

## 試験での問われ方

- 「RPOの説明として適切なものはどれか」
  → **復旧時に、どの時点のデータまで回復させるかを示す目標**
- **最頻出のひっかけ**：RTOとRPOの説明の入れ替え。
  **Point＝時点、Time＝時間の長さ**と英語で押さえると取り違えません
- 「RPOを24時間とする場合、適切なバックアップ運用はどれか」→ **1日1回の取得**
- 「RPOを0にするために必要なものはどれか」→ **リアルタイムのデータ同期**
- **科目B（記述式）**：「RTOとRPOの違いを述べよ」
  → **RTOは何時間以内に復旧するかの目標、RPOはどの時点のデータまで復旧するかの目標。**
  そのまま書ける形で暗記しておきます
