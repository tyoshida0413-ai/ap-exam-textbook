# 2相コミット

> **分散データベースで、全サイトの合意を確認してから確定する手順**。
> 複数サイトをまたいで[[ACID特性]]の**原子性**を保証する。

## 日常のたとえ

全員参加が条件のイベントを決めるとき、いきなり「明日集合」と伝えるでしょうか。
まず「明日来られますか」と全員に確認し、**全員がはいと答えてから**開催を確定します。
1人でも無理なら中止を伝えます。この2段階が2相コミットです。

## なぜそうなるのか

```
第1相（コミット準備）
  調停者 → 各サイト：「コミットできますか」
  各サイト：更新をログに書き、いつでも確定できる状態にしてから
            「はい（コミット可）」か「いいえ（中止）」を返す

第2相（コミット実行）
  全員が「はい」    → 調停者は全サイトへ「コミットせよ」
  1つでも「いいえ」 → 調停者は全サイトへ「ロールバックせよ」
```

**なぜ2段階なのか**：いきなりコミットを指示すると、あるサイトは成功し別のサイトは失敗する事態が
起こりえます。それでは「全員やる／全員やらない」が崩れ、全体の原子性が壊れます。
先に**全員が確定できることを確認してから**指示することで、これを防いでいます。

第1相で「はい」と答えたサイトは、**自分の判断ではもう中止できない状態**になります。
これを**セキュア状態**（コミット可能状態）といいます。

### 弱点：ブロッキング

第1相と第2相の間で**調停者が故障すると**、セキュア状態のサイトは
コミットしてよいのか中止すべきか自分では判断できず、**ロックを保持したまま待ち続けます**。
これを**ブロッキング**といいます。待っている間、そのデータは誰も使えません。

この弱点を減らすために段階をもう1つ増やした**3相コミット**もありますが、
通信回数が増えるため実用例は限られます。

## 混同しやすい語

| 語 | 決定的な違い |
|---|---|
| [[2相ロッキング]] | 名前が似ているだけの別物。あちらは**ロックの取得・解放の規則** |
| [[レプリケーション]] | あちらは**同じデータを複製して置く**技術。2相コミットは**確定の手順** |
| [[コミット]] | 1つのDBでの確定操作。2相コミットは**複数サイトにまたがる**場合の手順 |

## 試験での問われ方

- 「分散データベースで原子性を保証する仕組みは」→ **2相コミット**
- 「第1相で行われることは」→ **各サイトにコミット可否を問い合わせる**
- 「2相コミットの問題点は」→ **調停者の故障時にサイトが待ち続ける**（ブロッキング）
- ひっかけ：2相ロッキングと入れ替える
