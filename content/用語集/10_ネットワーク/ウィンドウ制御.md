# ウィンドウ制御

> [[TCP]]で、**確認応答（ACK）を待たずに連続して送ってよいデータ量を調整する仕組み**。
> この「まとめて送ってよい量」を**ウィンドウサイズ**という。

## 日常のたとえ

書類を1枚渡すたびに「受け取りました」の返事を待っていたら、100枚渡すのに100往復かかります。
現実には「**10枚まとめて渡して、まとめて返事をもらう**」ようにします。

ただし、**相手の机が小さければ10枚は置けません**。
相手が置ける枚数に合わせないと、床に落ちて（＝あふれて）しまいます。

## なぜそうなるのか

### 1つずつ確認していては遅い

送るたびに返事を待つ方式（ストップアンドウェイト）は確実ですが、
**往復の待ち時間が積み上がって非常に遅くなります**。
そこで、**返事を待たずに何個か先まで送ってしまう**のがウィンドウ制御です。

```
ウィンドウが小さい： 送 → 待 → 送 → 待 …  確実だが遅い
ウィンドウが大きい： 送送送送送 → まとめて確認  速いが、相手が処理しきれないとあふれる
```

### 誰の都合に合わせるのか ── ここが混乱の元

TCPは**2種類の事情**に合わせて送信量を変えます。**この2つの区別が試験の核心です。**

| 制御 | 何に合わせるか | たとえ |
|---|---|---|
| **フロー制御** | **相手（受信側）の処理能力** | 相手の机の広さに合わせる |
| **輻輳制御** | **途中の回線の混み具合** | 道路の渋滞に合わせる |

ウィンドウ制御は、このうち**フロー制御を実現する仕組み**です。
受信側が「**いま これだけ受け取れます**」とウィンドウサイズを毎回通知し、送信側はそれに従います。

### 輻輳制御ではどう動くか

回線が混んでいるとき（[[輻輳]]）に大量に送ると、**捨てられたパケットが再送され、さらに混みます**。
そこでTCPは、通信開始時は**小さく送り始めて、うまくいけば徐々に増やす**という動きをします
（**スロースタート**）。
「いきなり全力で送らない」のは、**悪循環を作らないため**です。

## 混同しやすい語

| 語 | 決定的な違い |
|---|---|
| フロー制御 | ウィンドウ制御は**フロー制御を実現する手段**。目的と手段の関係 |
| 輻輳制御 | **途中の回線**に合わせる。フロー制御は**相手**に合わせる。「誰の都合か」で区別する |
| [[3ウェイハンドシェイク]] | あちらは**接続を張る**手順。こちらは**接続後の流量**の調整 |
| [[帯域制御]] | あちらは**ネットワーク機器側**が通信種別ごとに帯域を割り当てる[[QoS]]の手法。こちらは**TCPが端末側**で行う調整 |

## 試験での問われ方

- 「**ウィンドウ制御の目的はどれか**」
  → **確認応答を待たずに送信できるデータ量を調整し、伝送効率を高める**
- 「受信側の処理能力に合わせて送信量を調整する制御はどれか」→ **フロー制御**
- 「ネットワークの混雑に応じて送信量を調整する制御はどれか」→ **輻輳制御**
- ひっかけ：フロー制御と輻輳制御の説明を入れ替える。**最頻出**
