# 3ウェイハンドシェイク

> [[TCP]]が通信を始めるときに行う、**3回のやり取りによる接続確立の手順**。
> **SYN → SYN/ACK → ACK** の順で、双方が「送れる」「受け取れる」ことを確認してからデータ転送に入る。

## 日常のたとえ

電話をかけたとき、いきなり本題から話し始める人はいません。

```
A「もしもし、聞こえますか？」        （呼びかけ）
B「はい、聞こえます。そちらは？」    （応答＋こちらからも確認）
A「はい、聞こえています」            （応答）
    → ここでようやく本題に入る
```

**3往復ではなく3回のやり取り**である点に注目してください。
Bの発言が「**応答**」と「**こちらからの確認**」を兼ねているので、4回ではなく3回で済んでいます。

## なぜそうなるのか

### 実際のやり取り

```
クライアント                         サーバ
    │ ── (1) SYN ───────────→ │  「接続したい」
    │ ←─ (2) SYN + ACK ─────── │  「いいですよ。私からもお願いします」
    │ ── (3) ACK ───────────→ │  「了解しました」
    │ ====== データ転送開始 ====== │
```

- **SYN**（synchronize ＝ 同期）＝ 接続の要求
- **ACK**（acknowledgement ＝ 確認応答）＝ 受け取ったという返事

### なぜ2回では足りないのか

**通信は双方向だからです。**

(1)と(2)で確認できるのは「**クライアント → サーバ**」が通じることだけです。
「**サーバ → クライアント**」が通じているかは、
**サーバから送った(2)が本当に届いたと分かるまで**確認できません。
それを知らせるのが(3)のACKです。

> **往路と復路を両方確認する**ために、最低3回のやり取りが必要になります。
> 「3回」という数字を丸暗記するのではなく、**双方向だから**と理解してください。

### 切断は4回

接続は3回ですが、切断は **FIN → ACK → FIN → ACK** の**4回**が基本です。
片方が「もう送るものはない」と言っても、**もう片方はまだ送りたいデータが残っているかもしれない**ため、
終了の意思表示を**それぞれが独立に**行うからです。

### この手順を悪用する攻撃

SYNだけを大量に送りつけ、**サーバに「接続待ち」の状態を大量に作らせて資源を枯渇させる**攻撃が
**SYN Flood攻撃**です。**3ウェイハンドシェイクを途中で止める**という手口で、
仕組みを知っていれば何が起きているか説明できます。

## 混同しやすい語

| 語 | 決定的な違い |
|---|---|
| [[UDP]] | **接続確立をしない**。いきなり送る。だから速い |
| [[ウィンドウ制御]] | あちらは**接続後にどれだけ送ってよいか**の調整。こちらは**接続を張る**手順 |
| 確認応答（ACK） | ACKは**個々のデータの受領確認**にも使われる。3ウェイハンドシェイクはそのうち**接続確立時**の使い方 |

## 試験での問われ方

- 「**3ウェイハンドシェイクの順序として正しいものはどれか**」
  → **SYN → SYN/ACK → ACK**
- 「TCPコネクションの確立に必要な最小のやり取り回数は」→ **3回**
- ひっかけ：ACKを先頭に置いた選択肢、SYN/ACKを分けて4回にした選択肢
- 記述式：「なぜ3回必要か」→ **往路と復路の双方が通じることを確認するため**
