## 絶対に守る6つのルール

1. **⛔ 教科書の基準はIPA出題範囲だけ。`応用情報単語リスト.md` は教科書の工程では開かない**（→ [[01_教科書の作成基準]]冒頭）。
   単語リストを参照してよいのは**用語集の工程（F1〜F5）に入ってから**
2. **⛔ 教科書が先、用語集が後。** 順序は動かさない。用語集を先に作るのはユーザーの明示指示があるときだけ
3. **想定読者は「情報系大学卒だがIT実務経験なし・基本情報レベル未満」。** たとえ話と「なぜ」を必ず書く

## 1. 2つの成果物と、その関係

このフォルダの成果物は2つ。**教科書がメインで、用語集はその拡張**という関係にある。

- **教科書**：IPA中分類ごとに1本（全23本）。通読して**体系を理解する**ためのもの
- **用語集**：1単語につき1ファイル。**分からない語を引く**ためのもの

> # ⛔ 大原則：教科書が先、用語集が後（順序は動かさない）
>
> - **教科書がメイン。用語集はそれを拡張するために存在する。**
> - **その分野の教科書が完成していない状態で、用語集を先に作ってはならない。**
>   （ユーザーから明示的な指示があった場合のみ例外）
> - 理由：用語集の各ファイルは「教科書：`[[分野名]]` の N 節」で**教科書へ必ずリンクする**設計になっている。
>   教科書が無ければこのリンクが張れず、**辞書から体系へ戻る導線が失われる**。
>   セキュリティで機能したのは、教科書が先にあったからこの相互リンクが成立したため。
>
> **1分野の正しい進め方（全5工程）**：
> ```
> (1) 教科書/<分野>.md を作る       ← ここが起点。これ抜きで(2)へ進まない【Opus】
>     基準は出題範囲詳細のみ。単語リストは開かない（→ [[01_教科書の作成基準]]冒頭）
>          ↓  ← ★ここから下が「用語集の工程」。単語リストを開いてよいのはここから
> (2) 用語集のF1（設計：難語選定・混同ペア表・見本3〜5本）【Opus】
>          ↓
> (3) 用語集のF2（量産：残り全語）【Sonnet】
>          ↓
> (4) 用語集のF3（難語だけレビュー）【Opus】
>          ↓
> (5) 【F5】教科書→用語集のリンク設定【Sonnet】 → [[02_リンク設定F5]]
>          ↑ ここまでやって初めて「相互に行き来できる網」が完成する。
>            (4)で終わらせるとリンクが片道のままになる
> ```

Obsidian／Quartz上で `[[SQLインジェクション]]` とリンクすると、
**ホバーで内容がポップアップ表示**され、逆に単語側からは「どの教科書で使われているか」が
**バックリンク**で分かる。孤立した用語集ではなく、**教科書と相互に行き来できる網**にすることが目的。

## 2. モデルの分担（重要）

### 全体の割り当て

| 作業 | モデル | 理由 |
|---|---|---|
| **教科書の執筆** | **Opus** | ↓ 2.1で詳述 |
| 用語集 F1（設計） | **Opus** | 難語選定・混同ペアの見極めは横断的判断が要る |
| 用語集 F2（量産） | **Sonnet** | 見本と一行定義がある定型的なコンテンツ生成 |
| 用語集 F3（レビュー） | **Opus** | 難語だけ点検（全件レビューはしない） |

### 2.1 なぜ教科書はOpusなのか（2026-08-02 実証にもとづく判断）

**用語集F2でSonnetが成功した理由**を裏返すと、教科書との差がはっきりする。

| | 用語集F2（Sonnetで成功） | 教科書 |
|---|---|---|
| 手本 | 見本4本＋教科書があった | **無い**（自分が手本を作る側） |
| 元ネタ | 一行定義が既にある | **無い**（分野の体系から組む） |
| 作業の性質 | 定義を膨らませる定型作業 | **章立ての設計＋たとえ話の創出** |
| 分量 | 1語 1,000〜1,500字 | **1本 15,000〜37,000字を一貫した品質で** |

**Sonnetの品質は実際に高い**（F3で難語42語をレビューし、技術的誤りはゼロだった。
MACの「夫婦共有の合言葉スタンプ」のように、教科書に無いたとえ話も自力で作れている）。

それでも教科書をOpusにするのは、**教科書が「手本を作る側」だから**。
用語集F2が成立したのは教科書という基準があったからで、
**その基準自体の品質が落ちると全体が連鎖的に劣化する**。
想定される失敗も「事実誤り」ではなく「**説明が平板になる**」ことであり、
これは想定読者（IT実務経験なし）にとって致命的になる。

> **ただしOpusも完璧ではない。**
> 「教科書の節に番号が無く、用語集13ファイルが存在しない節を参照した」という構造的欠陥は、
> Opusが書いた教科書に起因していた。**モデルに関わらず9章の検証は必須。**

**例外**：付録A（用語チェックリスト）と付録C（NotebookLMプロンプト集）は定型作業のため
Sonnetでも足りる。ただし分割の手間が節約効果を上回るなら、教科書1本を通してOpusで書いてよい。

### 2.2 用語集の3フェーズ

品質差が出るのは一部の用語だけなので、**Opusを使う場面を限定する**。

```
【フェーズ1】Opus … 分野ごとの「設計」
  ├ 難語リストの選定（その分野で品質が効く語を抽出）
  ├ 混同ペア表の作成（どの語とどの語が紛らわしいか）
  └ 難語の見本を3〜5本執筆（基準を示す）
        ↓
【フェーズ2】Sonnet … 量産
  └ 見本に沿って、その分野の残り全語を執筆
        ↓
【フェーズ3】Opus … 限定レビュー
  └ フェーズ1で挙げた「難語」だけを点検する（全件レビューはしない）
```

### なぜこの分担なのか

- 全語の大半は「一行定義を膨らませれば済む」**定型的なコンテンツ生成**。
  グローバルCLAUDE.mdの基準どおり、ここに上位モデルは不要。
- 一方、**たとえ話の質**と**混同ペアの見極め**は横断的な判断が要るためOpusが有効。
- **「全部Sonnetで作ってから全部Opusでレビュー」はしない。**
  数百ファイルを流し読みするレビューは、実質的に追認に終わり、手直しが必要な箇所を
  見落としたまま「レビュー済み」の体裁だけが残るため。

### 2.3 実行の形（セッションとサブエージェント）★2026-08-08 全面変更

> **⛔ 「フェーズが変わったら `/model` で切り替える」という従来の運用は廃止した。**

#### なぜ変えたか（実測にもとづく）

セッションログ13本（5,109ターン）を集計したところ、4分野の制作で**約1億6,615万トークン相当**を消費していた。成果物量の約350倍にあたる。内訳：

- **消費の約58%は「巨大なコンテキストを毎ターン読み直す費用」**（cache_read／cache_write）。実際に生成した本文は12%にすぎない
- 同一セッションでOpusとSonnetを往復させると、切替1回あたり**約34万トークン**のキャッシュ再作成が発生する
- さらに悪いのは、Sonnetに切り替えても**Opusで膨らんだ会話をそのまま引き継ぐ**こと。用語集の本文が会話に積み上がり（実測でコンテキスト中央値47.6万トークン）、以後の全ターンがその長さで課金される

詳細は [[00_トークン消費_調査と節約策]]。

#### 正しい実行の形

| 工程 | 実行の形 | モデル |
|---|---|---|
| 教科書の執筆 | **専用セッション**。1本を通しで書き、**途中で切らない** | Opus |
| 用語集F1（設計） | 教科書とは**別セッション** | Opus |
| 用語集F2（量産） | **サブエージェントに分割発注** | Sonnet |
| 機械検査 | `python3 検証.py <分野>`（**LLMを使わない＝0トークン**） | — |
| 用語集F3（レビュー） | 検証.pyが弾いた語＋難語だけを読む | Opus |
| F5（リンク設定） | **別セッション** | → [[02_リンク設定F5]] |

**工程の境目では必ずセッションを切る**（進捗表と引き継ぎ書を更新してから `/clear`）。

**教科書の執筆だけは例外で、1本を書き終えるまで切らない。**
章をまたぐたとえ話・文体・相互参照の一貫性が崩れるため。実測では教科書1本の執筆は
**コンテキスト10万以下・50ターン以内**に収まっており（セキュリティ第23/26ターン、
ネットワーク第28ターン、サービスマネジメント第46ターン）、そもそも切る必要がない。
**教科書の執筆は総消費の1%未満**なので、ここを節約対象にしてはいけない。

#### F2の発注テンプレート

自分自身のモデルは変更できないが、**サブエージェントのモデルは指定できる**（Sonnetを指定する）。

**1回につき15〜20語をまとめて渡す。1語1エージェントは赤字になる**
（起動の固定費が約2万トークンかかるため）。1分野あたりの起動は5〜8回まで。

発注に必ず含めるもの：

- 見本ファイルのパス（[[00_引き継ぎ]] の4章の見本4本）
- テンプレート（4章）と執筆ルール（5章）
- 対象語の一覧と、それぞれの**難度（易／難）・一行定義**
- 分量仕様（**難は1,000〜1,500字**。易は分量指定なし）
- **「難度は指定どおりに書くこと。勝手に変えない」**（罠#22の再発防止）

**返させるもの：作成したファイル名と `wc -c` の実測値の表だけ。本文は返させない。**
（本文を返させると親の会話に積もり、委譲した意味が消える）

#### 検収（省略しない）

1. `python3 検証.py <分野>` を実行し、**違反0**を確認する
2. **難語を1〜2本、実際に開いて見本と読み比べる**
3. 進捗表を更新する

> 機械検査は「ファイルが存在するか」ではなく「**仕様の量と密度を満たすか**」を見るためのもの。
> ただし**内容の技術的な正しさ・たとえ話の質・混同ペアの妥当性は検出できない**ので、
> F3（難語の内容レビュー）は省略しない。**機械検査はF3の代替ではなく前段。**

> **⛔「全部Sonnetで作ってから全部Opusでレビュー」は引き続き禁止**（→ このあとの「なぜこの分担なのか」）。
> 2026-08-08 に「安く作って完成品を1回だけレビューさせる」案を検討したが、
> (1) 数百ファイルの流し読みは追認に終わる、(2) 読み込んだ内容は以後の修正ターン全部に乗るため
> 「1回だけ」が成立せず現行F3の約2倍のコストになる、の2点で却下した。

## 3. フォルダ構成と命名

```
応用情報技術者試験/
├─ 00_引き継ぎ.md               ← このファイル（01〜03・99に分割済み。→ 0章の構成図）
├─ 応用情報単語リスト.md         ← 元ネタ（1011語・「用語 | 説明」形式）

│   └─ 11_セキュリティ.md         ← 完成（唯一の見本）
└─ 用語集/
    └─ 11_セキュリティ/           ← 完成（140ファイル）
        ├─ 00_混同しやすい語の一覧.md  ← F1の設計成果物 兼 学習用の対比表
        ├─ SQLインジェクション.md
        ├─ ソルト.md
        └─ …
```

### 命名ルール

- **フォルダ名の番号は、IPAの中分類番号に合わせる**（`教科書/11_セキュリティ.md` と `用語集/11_セキュリティ/` が対応する）
  - ただし `01` と `02` は単語リストの区分と中分類が完全には一致していない（両方が中分類2に一部かかる）。実害がないため、この近似を許容する
- **ファイル名は用語そのまま**（`SQLインジェクション.md`）。番号は付けない
  - 理由：`[[SQLインジェクション]]` とリンクしたときにファイル名がそのまま一致するため
- 記号を含む用語は、ファイル名に使えない文字だけ置換する
  - `/` → `-`（例：`JPCERT-CC.md`、`SSL-TLS.md`）
  - 本文の見出し（`# `）には**元の表記をそのまま書く**（`# JPCERT/CC`）

> **⚠️ `/` を含む用語へのリンクは必ずファイル名形式で書く**（2026-08-02 に実際に発生した不具合）
> `[[SSL/TLS]]` と書くと、Quartzは `/` を**パス区切り**と解釈し `ssl/tls` のような
> **存在しない階層**を指してリンクが切れる。表示テキストを保ちたい場合は次の形式を使う：
> ```
> ✕ [[SSL/TLS]]              → ssl/tls を指してリンク切れ
> ○ [[SSL-TLS|SSL/TLS]]      → 正しく解決し、表示は「SSL/TLS」のまま
> ```
> 対象：`SSL-TLS` / `JPCERT-CC` / `ISO-IEC 15408`
- 別名がある語は frontmatter の `aliases` に書く（`` `[[XSS]]` `` でも `` `[[クロスサイトスクリプティング]]` `` でも飛べるようにする。
  ただし[[02_リンク設定F5]]の罠#8のとおり、**教科書からリンクを張るときは alias 表記そのままではなく実ファイル名を主キーにすること**）

|---|---|---|

## 5. 執筆ルール

### 文体・レベル

- **想定読者：情報系の大学は出ているが、IT実務経験はなく基本情報レベル未満**
  （教科書 `11_セキュリティ.md` と同じ前提。あの文体をそのまま踏襲する）
- 専門用語を説明に使うときは、**その場で一言添えるか `[[リンク]]` を張る**
- 略語は初出時に**正式名称と、その意味**を書く（例：IDS＝Intrusion **Detection** System＝侵入「検知」）
- 丸囲み数字（①②③）は使わない。`(1)(2)(3)` を使う

### リンク

- 関連語は積極的に `[[用語名]]` で繋ぐ。**まだ存在しないファイルへのリンクでもよい**
  （後から作ったときに自動で繋がる。むしろ「作るべき語」の目印になる）
- **教科書へのリンクを必ず1本入れる**（`[[11_セキュリティ]]` のように）。
  辞書から体系に戻れる導線がこのプロジェクトの要

### やってはいけないこと

- **元の単語リストの一行説明をコピーしただけで済ませない。** 膨らませることが目的
- **教科書の文章をそのまま貼らない。** 辞書として単体で完結する書き方に組み直す
- **不確かな内容を断定で書かない。** 確信が持てない場合はWeb検索で裏を取る
- **`用語集/` を Quartz側（Googleドライブ）で編集しない**（→ 8章）

## 6. 難語の選定基準（フェーズ1で使う）

その分野の語を、次の基準で **易 / 難** に振り分ける。
**難と判定した語だけがフェーズ3（Opusレビュー）の対象**になる。

### 「難」に分類する語

- **たとえ話がないと理解できない**（公開鍵暗号、ソルト、ハイブリッド暗号）
- **鍵・向き・順序を取り違えやすい**（ディジタル署名の秘密鍵／公開鍵）
- **似た語と対で問われる**（IDS↔IPS、SPF↔DKIM↔DMARC、FAR↔FRR、27001↔27002）
- **「なぜ必要になったか」の因果が要る**（DMARC、ゼロトラスト、多要素認証）
- **計算式が絡む**（鍵の数 n(n−1)/2、稼働率、ALE＝SLE×ARO）

### 「易」に分類する語

- 制度名・組織名・規格名で、**定義を書けば足りる**（NISC、ISMAP、PCI DSS、CVE）
- 一般語に近く、説明が一意に定まる（情報資産、内部不正）

**目安：難は全体の2〜3割程度**

> **実績（2026-08-02 セキュリティ）**：138語中 **難42語（30%）／易96語**。
> 当初の想定（1〜2割）より多かった。セキュリティは対比で問われる語が特に密集する分野のため、
> 他分野ではこれより下がる可能性が高い。**行数と語数を取り違えない**こと
> （1行に複数語をまとめると集計がずれる。正はファイルの frontmatter `難度:`）。

> **⚠️ リンク切れ検査は必ずこの方法で行う**
> Quartzは未解決のwikilinkに `class="broken"` を**付けない**ため、
> `grep broken` では検出できない（2026-08-02 にこれで8件見逃した）。
> **出力HTMLのhrefを実ファイルと突き合わせる**のが唯一確実な方法：
>
> ```bash
> cd "<Quartzのpublic>"
> grep -rho 'href="[^"]*"' 用語集/<分野>/*.html \
>   | sed 's/href="//;s/"//' | grep -v '^http' | grep -v '^#' \
>   | grep -v '\.css$\|\.js$\|\.xml$\|\.webp$\|\.png$\|\.ico$' \
>   | sed 's|^\.\./\.\./||' | sort -u \
>   | while read -r h; do h="${h%/}"; [ -z "$h" ] && continue; \
>       [ ! -f "$h.html" ] && [ ! -f "$h/index.html" ] && [ ! -d "$h" ] && echo "切れ: $h"; done
> ```
>
> 検出された語は次のいずれかで処理する：
> (1) 単語リストに**ある** → 後で作られるので放置してよい
> (2) 単語リストに**ない**が対比の要・頻出 → **ページを新規作成し、単語リストにも追加する**（→ 下記ルール）
> (3) 単語リストに**なく**説明も他ページで足りる → **ブラケットを外して平文にする**
