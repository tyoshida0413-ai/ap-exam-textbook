## 1. 結論（先に3行）

- **消費の約50%は「Opusが巨大なコンテキストを毎ターン読み直す費用（cache_read）」**であり、教科書本文や用語集の「生成」そのものは全体の12%にすぎない。
- 原因は **1セッションが長すぎる**（最大1,143ターン）ことと、**生成した用語集・教科書の本文が全部メインの会話に積み上がったまま**であること。サブエージェントへの委譲は**13セッションで0件**だった。
- **量産工程をサブエージェントに出し、工程ごとにセッションを切る**だけで、体感で6〜7割の削減が見込める。ここは作業内容を一切減らさずに削れる部分。

## 3. 何にトークンを使っていないか（先に潰しておく誤解）

ツールの往復そのものは**ほとんど効いていない**。実測：

| ツール | 回数 | 送信文字 | 返却文字 | 結果の中央値 |
|---|---:|---:|---:|---:|
| Bash | 1,266 | 747,267 | 959,442 | 352字 |
| Read | 300 | 55,346 | 700,880 | 1,125字 |
| Write | 515 | 895,117 | 128,945 | — |
| Edit | 560 | 529,733 | 138,645 | — |

全部足しても約400万字（約300万トークン）で、総消費1億6,615万の**2%未満**。
つまり「ファイルを読みすぎている」「コマンドの出力が大きい」は主因ではない。
**主因は、それらが積み上がった会話全体を、その後の全ターンで何百回も読み直していること。**

## 4. 主因の特定（4つ、証拠つき）

### 主因1：セッションが長く、コンテキストが巨大なまま数百〜千ターン回っている【最大】

- cache_read は**1ターンごとに、その時点のコンテキスト全長ぶん**発生する。
- aa23b6db は中央値47.6万トークンのコンテキストで1,143ターン。→ 47.6万 × 1,143 ＝ **約5.4億トークン**。この1セッションだけで全体の3分の1。
- コンテキストが2倍になると、以降のターン単価も2倍になる。**後半のターンほど1回が高い。**

### 主因2：生成した用語集・教科書の本文が、全部メインの会話に残り続けている

- Write 515回。用語集は416ファイル＝ほぼ1語1回のWrite。1語2,000〜3,000字。
- 1分野100語なら **25万字（約20万トークン）が会話に積もる**。これがコンテキスト中央値47万の正体。
- **サブエージェント（Agentツール）の呼び出しは13セッション通じて0件**。すべてメインの会話で作っている。

### 主因3：Sonnetでの量産中もキャッシュが効いていない

- Sonnetは2,245リクエストで cache_write 6,244万＝**1リクエストあたり27,800トークンの書き込み**。Opusは8,400／リクエスト。**3.3倍**。
- 同一セッション内でOpusとSonnetを`/model`で往復させているため（例：d228c731 は opus 363回・sonnet 391回が混在）、キャッシュが分断されて書き直しが頻発している。
- モデル切替の直後だけを見ても、1回あたり **343,834トークン**のキャッシュ再作成が発生（20回で計688万）。

### 主因4：ターン数そのものの多さ

- Bash 1,266回のうち **689回が `cd` から始まる単発コマンド**。sleep 35回・pkill 23回・curl 17回・gh 23回はデプロイ確認の往復。
- 1ターン減らすことは、その時点のコンテキスト長（後半なら40万超）をまるごと減らすこと。**個々のコマンド出力を削るより、往復回数を削るほうが2桁効く。**

## 5. 節約策（効果の大きい順）

### 対策A：量産・検証をサブエージェントに委譲する【最優先・効果最大】

`/model` でSonnetに切り替えるのをやめ、**Agentツールでサブエージェントを起動する**。

| | 現行（/model切替） | 改善案（サブエージェント） |
|---|---|---|
| 生成した用語集本文 | メインの会話に全部残る | サブエージェント内で消える |
| 親に返るもの | 全文 | 「20語完了・実測字数一覧」だけ |
| キャッシュ | Opus/Sonnet往復で分断 | 親のキャッシュは無傷 |
| 親のコンテキスト | 47万まで膨張 | 10万前後で安定 |

具体的な使い方：

```
用語集F2の量産 → 15〜20語ずつサブエージェント（model: sonnet）に分割発注。
  プロンプトに含めるもの：見本ファイルのパス／テンプレート／対象語リスト／字数仕様
  返させるもの：作成ファイル名と wc -c の実測値の表のみ（本文は返させない）
F3の機械検証（リンク切れ・字数・メタデータ照合） → サブエージェントに丸ごと委譲し、違反リストだけ返させる
```

**注意1（検収）**：親が受け取るのが要約だけになるぶん、CLAUDE.mdの検収ルール（分量実測・メタデータ照合・1〜2本を目視）は**これまで以上に厳格に**適用する。委譲＝検収を緩めるではない。

**注意2（委譲の粒度）**：2026-08-08 の別調査で「サブエージェントの多用がむしろ消費の大半を占める」という実務報告に触れている。これは**細切れ起動をした場合に正しい**。サブエージェントは起動のたびにシステムプロンプト・ツール定義・スキル一覧で概ね2万トークン前後の固定費がかかるため、

- **1語1エージェント → 完全に赤字**（固定費2万 vs 生成2,000トークン）
- **15〜20語1エージェント → 十分にペイする**（固定費2万 vs 生成4万＋親のコンテキスト膨張回避）

したがって「サブエージェントを使うか否か」ではなく、**1回の発注に十分な作業量を束ねること**が条件になる。目安は**1エージェントあたり生成4万トークン以上、起動は1分野あたり5〜8回まで**。細かい調べ物のたびに起動するのは避ける。

### 対策B：工程ごとにセッションを切る（`/clear`）

`教科書執筆` → `F1設計` → `F2量産` → `F3レビュー` → `F5リンク設定` の**境目で必ずセッションを切る**。
引き継ぎ書の「3分ブリーフィング」節があるので再開コストは1万トークン程度。
一方、切らずに続けると以後の全ターンが40万超の単価になる。**切るコストのほうが圧倒的に安い。**

目安：**コンテキストが15万トークンを超えたら、工程の途中でも引き継ぎ書を更新してセッションを切る。**

> **⛔ ただし教科書の執筆だけは、1本を必ず1セッションで通す。途中で切らない。**
> 理由と実測の裏づけは8章。教科書執筆は実測でコンテキスト10万以下・50ターン以内に収まっており、
> この目安に抵触しない。**切るのは「教科書を書き終えた直後」であって、執筆の途中ではない。**

### 対策C：ターン数を減らす

- Bashは**独立した複数コマンドを1回にまとめる**（検証コマンド群は1本のスクリプトにして、結果サマリだけ出力）。
- デプロイ確認の `sleep`→`curl`→`sleep` のポーリングをやめ、**1回のコマンドで待機ループ**を回して最終結果だけ返す。
- 完了検証（9章のチェックリスト）を**1本の検証スクリプト**にまとめ、`検証.py` として保存する。毎回コマンドを組み立て直さない。

### 対策D：`00_引き継ぎ.md`（166KB・1,521行）を分割する

- 現状Read 39回・Edit 128回。全文を一度でも読むと**約5.5万トークンが以後ずっとコンテキストに残る**。
- 分割案：
  - `00_引き継ぎ.md` … ブリーフィング＋ルール＋罠＋進捗表のみ（20KB以内）
  - `01_教科書の作成基準.md` … 2.5章
  - `02_リンク設定F5.md` … 2.6〜2.7章
  - `03_サイト実装メモ.md` … 2.8〜2.10章（サイト表示・サイドパネル・付箋。教科書作業では不要）
- 教科書執筆時に読むのは `00` と `01` だけになる。

### 対策E：モデル切替を同一セッション内で行わない

対策A・Bを実施すれば自動的に解消する。引き継ぎ書2章の「フェーズが変わったら`/model`で切り替えを依頼する」という記述を、**「フェーズが変わったらセッションを切る／サブエージェントに出す」**に改める必要がある。

### 対策F：書き直しを出さない

- セキュリティ教科書は想定読者を外して**全面書き直し**（65,023字を2回Write）になった。1回の書き直しで約13万トークン相当の損失。
- 2.5章の「割付表を作ってから執筆」は既に確立済み。**これを守ることが最大の節約でもある**という位置づけを明記しておく。

### 対策G：`/token-diet` は用語集・サイト作業でのみ使う（教科書執筆では使わない）

既存スキルには「対象外（このモードでも節約しない）＝読み落としが実害になるタスクは全文読みを維持」という条項がある。
**教科書執筆はまさにこれに該当する**（出題範囲詳細を部分読みすると、2026-08-03 ネットワークの出題範囲抜けが再発する）。
したがって `/token-diet` を打つのは **F2量産・サイト実装・調査作業の開始時のみ**とする。

### 結論：落ちない。**教科書執筆は総消費の1%未満で、そもそも節約対象にする必要がない。**

**教科書の本体執筆は、どの分野でも第50ターン以内・コンテキスト10万以下で完了していた。**
概算で1本あたり200〜300万トークン相当、**総消費1億6,615万の1%未満**。

一方、同じセッションはその後 712〜1,143ターンまで続き、コンテキストが47万まで膨らんでいる。

| セッション | 総ターン | コンテキスト中央値 | 後半で何をしていたか |

**コストを膨らませていたのは、教科書を書き終えたあと同じセッションで続けた用語集の量産である。**
教科書執筆はその手前の「まだ安い区間」で完了している。

### したがって、教科書には次を保証したうえで削減目標をほぼ全額達成できる

教科書執筆フェーズでは**現状を一切変えない**：

- Opusを使う（変更なし）
- `応用情報技術者試験_出題範囲詳細.md` は**全文読む**（`/token-diet` の対象外。部分読みしない）
- 1本を**1セッションで通しで書く**（章をまたぐたとえ話・文体・相互参照の一貫性を守るため）
- 割付表を作ってから執筆する手順（2.5章）を維持する

**切るのは「教科書を書き終え、進捗表を更新した直後」。** ここで`/clear`し、用語集の工程は別セッションで始める。

### 品質リスクが実際に残るのは1点だけ：対策A（用語集F2のサブエージェント委譲）

これは**用語集の品質**の話であって教科書の品質ではないが、正直に書く。

- 委譲で失われるのは「Opusが作った見本とF1の設計判断が会話に載っている」という暗黙の文脈。サブエージェントには明示的に渡さないと届かない。
- ただし **2026-08-04 の品質事故（難語19本が仕様1,000〜1,500字に対し300〜450字、メタデータの無断書き換え）は、現行の`/model`切替方式ですでに起きている**。暗黙の文脈は現状でも効いていない。

## 9. 「安く作って、完成品を1回だけレビューする」案の検討（2026-08-08）

### 提案

> 対策を講じた形（サブエージェント委譲など）で作成し、完成したものをまとめてレビューさせる。
> 読ませるのは1回だけなのでトークンも節約できるのではないか。

### 結論：作成側は採用、レビュー側は採用しない。代わりに**機械検査を挟む**。

### 却下の理由1：既存の決定と衝突する

`00_引き継ぎ.md` 2章に明記されている。

> **「全部Sonnetで作ってから全部Opusでレビュー」はしない。**
> 数百ファイルを流し読みするレビューは、実質的に追認に終わり、手直しが必要な箇所を
> 見落としたまま「レビュー済み」の体裁だけが残るため。

### 却下の理由2：トークンでも安くならない

「読ませるのは1回だけ」という前提が成立しない。**読み込んだ内容は、その後の修正ターン全部に乗り続ける。**
1回の読み込みの代金は読んだ瞬間ではなく、**その後のターン数**で決まる（→ 主因1）。

| 方式 | 読み込み | 実質コスト |
|---|---:|---|
| 全件を親に読ませてレビュー | 約6万トークン（1分野の用語集全文） | 6万 × 以後のターン数（50ターンなら約300万） |
| 現行F3（難語のみ） | 約3万トークン | 上記の約半分 |
| **機械検査 → 弾かれた語だけ** | **0トークン → 該当分のみ** | **最安** |

### 採用案：スクリプトで一括検査し、弾かれたものだけLLMが読む

「1回にまとめて安く」という狙いは正しい。ただし**まとめるのはLLMの読み込みではなく、機械検査のほう**。

2026-08-08 に `検証.py` を作成し、**LLMに1本も読ませずに** 412本全部を検査できることを実証した。

```bash
python3 検証.py              # 全分野
python3 検証.py 10_ネットワーク  # 分野指定
python3 検証.py --list       # 違反ファイルのパスのみ（加筆作業の入力用）
```

検査項目：難度別の分量／必須セクション（難語のみ「なぜそうなるのか」を必須にする）／
一言定義／frontmatter（title・分野・難度）／教科書リンクの有無と形式／丸囲み数字／リンクの入れ子の破損。

**2026-08-04 の事故は、この検査で全部検出できる内容だった。**

### 運用フロー（F2完了後）

```
F2量産（サブエージェント委譲）
   ↓
python3 検証.py          ← 0トークン。仕様違反を全件抽出
   ↓
違反ファイルだけをOpusが読んで修正   ← ここで初めてLLMが読む
   ↓
F3（難語の内容レビュー）  ← スクリプトが検出できない「内容の正しさ・たとえ話の質」だけを見る
```

**スクリプトが検出できないもの**：内容の技術的な正しさ、たとえ話の質、混同ペアの妥当性。
ここはLLMが読むしかないので、F3（難語のみOpus）は今後も残す。**機械検査はF3の代替ではなく前段。**
