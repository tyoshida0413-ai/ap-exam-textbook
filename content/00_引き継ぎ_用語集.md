# 用語集プロジェクト 引き継ぎドキュメント

> **このファイルの役割**
> `用語集/` の作成作業を、セッションをまたいで・モデルをまたいで同じ品質で継続するための唯一の基準書。
> **作業を始める前に必ず全文を読むこと。** 書式・分担・進捗はすべてここで管理する。

---

## 1. 何を作るのか

**1単語につき1ファイル**の辞書を作る。教科書（`教科書/`）の補強であり、**辞書的に「引く」用途**を想定している。

### 教科書との役割分担

| | 教科書（`教科書/`） | 用語集（`用語集/`） ← いま作るもの |
|---|---|---|
| 単位 | IPA中分類ごと（全23本） | **1単語ごと**（全966語） |
| 読み方 | 通読して体系を理解する | **分からない語を引く** |
| 分量 | 1本 15,000〜35,000字 | 1語 **1,000〜1,500字** |
| 役割 | 「なぜそうなるか」の筋道 | その語の**単体での完結した理解** |

### なぜ1ファイル1単語なのか

Obsidian／Quartz上で `[[SQLインジェクション]]` とリンクすると、
**ホバーで内容がポップアップ表示**され、逆に単語側からは「どの教科書で使われているか」が
**バックリンク**で分かる。孤立した用語集ではなく、**教科書と相互に行き来できる網**にすることが目的。

## 2. モデルの分担（重要）

品質差が出るのは一部の用語だけなので、**Opusを使う場面を限定する**。

```
【フェーズ1】Opus … 分野ごとの「設計」
  ├ 難語リストの選定（その分野で品質が効く語を抽出）
  ├ 混同ペア表の作成（どの語とどの語が紛らわしいか）
  └ 難語の見本を3〜5本執筆（基準を示す）
        ↓
【フェーズ2】Sonnet … 量産
  └ 見本に沿って、その分野の残り全語を執筆
        ↓
【フェーズ3】Opus … 限定レビュー
  └ フェーズ1で挙げた「難語」だけを点検する（全件レビューはしない）
```

### なぜこの分担なのか

- 966語の大半は「一行定義を膨らませれば済む」**定型的なコンテンツ生成**。
  グローバルCLAUDE.mdの基準どおり、ここに上位モデルは不要。
- 一方、**たとえ話の質**と**混同ペアの見極め**は横断的な判断が要るためOpusが有効。
- **「全部Sonnetで作ってから全部Opusでレビュー」はしない。**
  966ファイルを流し読みするレビューは、実質的に追認に終わり、手直しが必要な箇所を
  見落としたまま「レビュー済み」の体裁だけが残るため。

### モデル切り替えのタイミング

Claude側からモデルは変更できない。**フェーズが変わったら、ユーザーに `/model` での切り替えを依頼する。**

## 3. フォルダ構成と命名

```
応用情報技術者試験/
├─ 00_引き継ぎ_用語集.md        ← このファイル
├─ 応用情報単語リスト.md         ← 元ネタ（966語・「用語 | 説明」形式）
├─ 教科書/
│   └─ 11_セキュリティ.md
└─ 用語集/                       ← 新設
    ├─ index.md                  ← 全分野への入口・索引
    ├─ 01_基礎理論・アルゴリズム/
    │   ├─ 2の補数.md
    │   └─ ハフマン符号.md
    ├─ 11_セキュリティ/
    │   ├─ SQLインジェクション.md
    │   └─ ソルト.md
    └─ …
```

### 命名ルール

- **フォルダ名の番号は、IPAの中分類番号に合わせる**（`教科書/11_セキュリティ.md` と `用語集/11_セキュリティ/` が対応する）
  - ただし `01` と `02` は単語リストの区分と中分類が完全には一致していない（両方が中分類2に一部かかる）。実害がないため、この近似を許容する
- **ファイル名は用語そのまま**（`SQLインジェクション.md`）。番号は付けない
  - 理由：`[[SQLインジェクション]]` とリンクしたときにファイル名がそのまま一致するため
- 記号を含む用語は、ファイル名に使えない文字だけ置換する
  - `/` → `-`（例：`JPCERT-CC.md`、`SSL-TLS.md`）
  - 本文の見出し（`# `）には**元の表記をそのまま書く**（`# JPCERT/CC`）

> **⚠️ `/` を含む用語へのリンクは必ずファイル名形式で書く**（2026-08-02 に実際に発生した不具合）
> `[[SSL/TLS]]` と書くと、Quartzは `/` を**パス区切り**と解釈し `ssl/tls` のような
> **存在しない階層**を指してリンクが切れる。表示テキストを保ちたい場合は次の形式を使う：
> ```
> ✕ [[SSL/TLS]]              → ssl/tls を指してリンク切れ
> ○ [[SSL-TLS|SSL/TLS]]      → 正しく解決し、表示は「SSL/TLS」のまま
> ```
> 対象：`SSL-TLS` / `JPCERT-CC` / `ISO-IEC 15408`
- 別名がある語は frontmatter の `aliases` に書く（`[[XSS]]` でも `[[クロスサイトスクリプティング]]` でも飛べるようにする）

## 4. 1ファイルのテンプレート（厳守）

```markdown
---
title: SQLインジェクション
aliases:
  - SQLi
分野: 11_セキュリティ
難度: 難          # 易 / 難 のいずれか（→ 6章の基準）
---

# SQLインジェクション

> 入力欄にSQL文の断片を混ぜ込み、データベースに意図しない命令を実行させる攻撃。

## 日常のたとえ

（身近な場面に置き換える。ITの前提知識ゼロでも情景が浮かぶこと）

## なぜそうなるのか

（仕組み・原理。「なぜこの問題が起きるのか」「なぜこの対策が効くのか」）

## 混同しやすい語

| 語 | 決定的な違い |
|---|---|
| [[クロスサイトスクリプティング]] | あちらは情報を「盗む」／こちらは操作を「実行させる」 |

## 試験での問われ方

- 「対策として適切なものはどれか」→ **プレースホルダ**（エスケープは次善策）
- ひっかけ：〜

## 関連

[[WAF]] ／ [[セキュアプログラミング]] ／ [[プレースホルダ]]

教科書：[[11_セキュリティ]] の 2.2 節
```

### 見本ファイル（執筆前に必ず読むこと）

書式の基準はこの4本。**型が違うものを選んである**ので、書く語に近いものを真似る。

| 見本 | 型 | 何の見本か |
|---|---|---|
| `用語集/11_セキュリティ/ディジタル署名.md` | 難 | **鍵の向き**のような取り違えを、対比表と原則で潰す型 |
| `用語集/11_セキュリティ/ソルト.md` | 難 | **なぜ効くのか**を、攻撃側の動機から順に説明する型 |
| `用語集/11_セキュリティ/DMARC.md` | 難 | **必要になった順**で因果を追う型（3語セットの一員） |
| `用語集/11_セキュリティ/NISC.md` | 易 | **たとえ話・混同ペアを省略した型**。制度名・組織名はこれでよい |

### セクションの増減ルール

- **「日常のたとえ」は、無理なら省略してよい**。こじつけたたとえ話は理解を妨げるため、
  自然な比喩が思いつかない語（`CVE`、`NISC` など固有名詞・制度名）では書かない
- **「混同しやすい語」は、実際に紛らわしい相手がいるときだけ**置く。埋めるために無理に作らない
- 逆に、**「一言定義」「関連」は全語で必須**

## 5. 執筆ルール

### 文体・レベル

- **想定読者：情報系の大学は出ているが、IT実務経験はなく基本情報レベル未満**
  （教科書 `11_セキュリティ.md` と同じ前提。あの文体をそのまま踏襲する）
- 専門用語を説明に使うときは、**その場で一言添えるか `[[リンク]]` を張る**
- 略語は初出時に**正式名称と、その意味**を書く（例：IDS＝Intrusion **Detection** System＝侵入「検知」）
- 丸囲み数字（①②③）は使わない。`(1)(2)(3)` を使う

### リンク

- 関連語は積極的に `[[用語名]]` で繋ぐ。**まだ存在しないファイルへのリンクでもよい**
  （後から作ったときに自動で繋がる。むしろ「作るべき語」の目印になる）
- **教科書へのリンクを必ず1本入れる**（`[[11_セキュリティ]]` のように）。
  辞書から体系に戻れる導線がこのプロジェクトの要

### やってはいけないこと

- **元の単語リストの一行説明をコピーしただけで済ませない。** 膨らませることが目的
- **教科書の文章をそのまま貼らない。** 辞書として単体で完結する書き方に組み直す
- **不確かな内容を断定で書かない。** 確信が持てない場合はWeb検索で裏を取る
- **`用語集/` を Quartz側（Googleドライブ）で編集しない**（→ 8章）

## 6. 難語の選定基準（フェーズ1で使う）

その分野の語を、次の基準で **易 / 難** に振り分ける。
**難と判定した語だけがフェーズ3（Opusレビュー）の対象**になる。

### 「難」に分類する語

- **たとえ話がないと理解できない**（公開鍵暗号、ソルト、ハイブリッド暗号）
- **鍵・向き・順序を取り違えやすい**（ディジタル署名の秘密鍵／公開鍵）
- **似た語と対で問われる**（IDS↔IPS、SPF↔DKIM↔DMARC、FAR↔FRR、27001↔27002）
- **「なぜ必要になったか」の因果が要る**（DMARC、ゼロトラスト、多要素認証）
- **計算式が絡む**（鍵の数 n(n−1)/2、稼働率、ALE＝SLE×ARO）

### 「易」に分類する語

- 制度名・組織名・規格名で、**定義を書けば足りる**（NISC、ISMAP、PCI DSS、CVE）
- 一般語に近く、説明が一意に定まる（情報資産、内部不正）

**目安：難は全体の2〜3割程度**

> **実績（2026-08-02 セキュリティ）**：138語中 **難42語（30%）／易96語**。
> 当初の想定（1〜2割）より多かった。セキュリティは対比で問われる語が特に密集する分野のため、
> 他分野ではこれより下がる可能性が高い。**行数と語数を取り違えない**こと
> （1行に複数語をまとめると集計がずれる。正はファイルの frontmatter `難度:`）。

## 9. 完了前チェックリスト

1ファイルごとに確認する。

- [ ] frontmatter に `title` / `分野` / `難度` がある
- [ ] 一言定義（`>` の引用）が1〜2文で書けている
- [ ] 元の単語リストの一行説明の**コピーになっていない**
- [ ] 略語は正式名称と意味が書かれている
- [ ] `[[リンク]]` が最低1本（教科書へのリンクを含む）ある
- [ ] たとえ話は**自然か**（こじつけなら削除する）
- [ ] 1,000〜1,500字に収まっている
- [ ] ファイル名に `/` などの使用不可文字が入っていない

分野を終えたら：

- [ ] **語数の突合**：元の単語リストと作成済みファイルの `title` を `diff` で照合し、差分0を確認した
- [ ] **リンク切れ検査**：下記コマンドで「実体が存在しないリンク」が0件であることを確認した
- [ ] **教科書の節番号が実在するか**確認した（`grep '^#\{2,3\} ' 教科書/*.md` と突合）
- [ ] 進捗表を更新した
- [ ] `sync-content.sh` で公開サイトに反映した
- [ ] Daylogに記録した

> **⚠️ リンク切れ検査は必ずこの方法で行う**
> Quartzは未解決のwikilinkに `class="broken"` を**付けない**ため、
> `grep broken` では検出できない（2026-08-02 にこれで8件見逃した）。
> **出力HTMLのhrefを実ファイルと突き合わせる**のが唯一確実な方法：
>
> ```bash
> cd "<Quartzのpublic>"
> grep -rho 'href="[^"]*"' 用語集/<分野>/*.html \
>   | sed 's/href="//;s/"//' | grep -v '^http' | grep -v '^#' \
>   | grep -v '\.css$\|\.js$\|\.xml$\|\.webp$\|\.png$\|\.ico$' \
>   | sed 's|^\.\./\.\./||' | sort -u \
>   | while read -r h; do h="${h%/}"; [ -z "$h" ] && continue; \
>       [ ! -f "$h.html" ] && [ ! -f "$h/index.html" ] && [ ! -d "$h" ] && echo "切れ: $h"; done
> ```
>
> 検出された語は次のいずれかで処理する：
> (1) 966語リストに**ある** → 後で作られるので放置してよい
> (2) 966語リストに**ない**が対比の要 → **ページを新規作成する**
> (3) 966語リストに**なく**説明も他ページで足りる → **ブラケットを外して平文にする**
